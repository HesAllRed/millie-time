03

The share ladder

One problem drives all of this: iOS drops the text field when files are attached — widely reported, still open, and not technically a spec violation, so there's no version where it's guaranteed fixed. The print defeats it by making the captions pixels. Each rung below is a strictly more conservative payload than the one above.

RungThe callIf it works
1 share({ files: [print, …photos], text }) One tap. Everything arrives, plus selectable text as a bonus.
2 share({ files: [print, …photos] }) Still one tap. The files-only shape iOS handles predictably. Captions arrive regardless — they're in the print.
3 share({ text }) then share({ files }) Two taps. Both shapes bulletproof alone; she picks the recipient twice. Screen 09.
4 Clipboard + camera roll Nothing was lost. Everything she needs is already on her phone. Screen 11.

Rungs 1 and 2 are both a single tap, so the realistic outcome is one. The clipboard write happens first on every attempt, unconditionally.

You asked me to research alternatives for carrying the words. For the record, and in case her recaps ever grow: one card per day means 8 images that iMessage grid-collapses without guaranteeing order — numbering fixes comprehension, not clutter. A PDF keeps order perfectly but lands as a document attachment, so the photos never reach the recipient's camera roll. A hosted link needs a backend and puts her photos on a server, against the whole privacy posture. And if the weekly total ever passed roughly 3,000 characters, the single print stops being readable at thumbnail size and rung 3 should become the default instead.

05

Under the hood

You asked about SOLID, extensibility, and pushing updates. Short version: native ES modules, no build step, and SOLID applied only where it pays. Full reasoning in PLAN.md §2.5.

Module seams

config.js ← everything personal
state.js ← one store, subscribe
exif.js ← pure · tested
dates.js ← pure · tested
compose.js ← pure · tested
share/ ← open/closed lives here
  words · photos · clipboard
views/ ← deliberately concrete
  intake · sort · deck · send · debug

S and D fall out naturally. O applies only to share/ and the renderers — the two things device testing will change. L and I need class hierarchies this app has no reason to have; forcing them would be cargo cult. The three pure modules are unit-tested with node --test, built into the Node you already have. No jest, no config, no dependencies.

config.js

    "work hunty nola",

  sentWord: "nice",

  weekLength: 8,
  weekEndsOn: "newestPhoto",

One file, no logic to read. One real constraint: Google Fonts over CDN can't work offline and blocks first paint, so the selectable faces get self-hosted as woff2 and precached (~30 KB each). That makes it a curated set rather than "any font" — better anyway, since it keeps the app working on a plane.

Emoji in the print: yes. Canvas draws colour emoji natively on iOS as long as the font stack ends in Apple Color Emoji. The trap is line-wrapping — splitting a string by character shreds emoji into broken boxes, so the renderer wraps by grapheme via Intl.Segmenter (Safari 14.1+). Emoji in the caption fields and the shared text are free either way.

Pushing an update

edit → git push → live in ~30s

No install, no bundle, no dependency graph that rotted since last time. The fiddly part is the service worker, whose whole job is serving cached files:

• CACHE_VERSION bumped per release; old caches dropped on activate.
• _headers sets no-cache on sw.js — the concrete reason we're on Cloudflare not GitHub Pages.
• Applies on her next cold launch. iOS kills backgrounded PWAs often, so that's usually same-day.
• Need it now? Version stamp in the footer, tapped 3×, clears caches and reloads.
• Preview deploys mean you verify on your iPhone before her icon ever points at it.
